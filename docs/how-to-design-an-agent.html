How to think when you build an agent

Start from a job you already repeat. Decide what the agent may see and touch. Decide how you will check its work before you write it. This page walks through that with one real agent, built for a job you run every day.

What I looked at

Your history points to one job

I read the titles of about 50 of your sessions, and the contents of the ones about agents, subagents, memory and your daily news task. I did not open sessions about personal paperwork.

  • You learn by asking questions, then building. Your own learning map lists 13 agent components, each as questions you want answered.
  • Your weakest areas on that map were subagents (20%), context engineering, the Agent SDK and automation (30% each). Since then you built 7 subagents in this repo, plus a hook and a scorer.
  • Every agent so far reviews or fixes code or text. None of them researches the web, and none remembers anything between runs.
  • Your daily AI news task ran 11 times between November 4 and 15. It is the one job you already repeat. Its last run showed three weak points: general searches returned old pages, big claims came only from newsletters, and the phone notification was skipped.

So the next agent should be a researcher that remembers and can be checked. That is the daily news job.

The thinking process

Seven questions, in this order

The order matters. Questions 1 and 6 come first in practice, because you cannot judge an agent until you know what good output looks like.

  1. What result do I want, and who reads it?

    Write the output first. For the news job: a brief you can read on a phone, where each claim says how sure it is.

    GOES IN description, output format

  2. Should this be an agent at all?

    Use the simplest thing that works. The picture below shows the three tests.

    GOES IN a script, a skill, or an agent

  3. What must it know, and what should it distrust?

    An agent starts each run with a blank mind. Give it the date, the format and what went wrong last time. Treat anything it reads online as data, never as orders.

    GOES IN the prompt

  4. What may it touch?

    Give the fewest tools that do the job. Anything it must never do is enforced by a hook, not by a sentence in the prompt.

    GOES IN tools, hooks

  5. What should it remember?

    Only what makes the next run better: what it already reported, and which sources misled it. Decide how old notes get deleted.

    GOES IN memory

  6. How will I know it worked?

    Write the check before the agent. Ten rules a script can test beat a feeling that the brief looks fine.

    GOES IN a skill with a scorer

  7. How does it run, and what does it cost?

    Pick the cheapest model that passes the check. Cap its turns. Keep the notification step outside the agent, so the agent never acts on the world by itself.

    GOES IN model, effort, maxTurns, the schedule

Question 2 as a picture

Should this be an agent at all?

A script is free and exact. A skill is a recipe you run with Claude beside you. Reach for an agent only when the job needs its own clean context, limited tools, or has to run with no one watching.

The news job fails the first two tests. It needs judgment about sources, and it runs unattended every morning.

The worked example

ai-news-briefer, one answer per question

The files are on a new branch, feat/ai-news-briefer, and are not committed yet.

DecisionWhere it lives
1A brief with a headline, a phone-length push line, and 3 to 8 items, each tagged CONFIRMED, REPORTED or UNVERIFIEDskills/ai-brief-format/SKILL.md

This is the front matter. Each line answers one of the questions above.

---
name: ai-news-briefer
description: Researches the last day of AI news and returns a verified,
  phone-sized briefing. The caller must pass today's date.
tools: WebSearch, WebFetch
model: sonnet
effort: medium
maxTurns: 25
memory: user
skills:
  - ai-brief-format
hooks:
  PreToolUse:
    - matcher: "WebFetch"
      hooks:
        - type: command
          command: 'bash "$CLAUDE_PROJECT_DIR/.claude/hooks/ai-news-guard.sh"'
---

Left out on purpose. isolation: worktree, because it writes no code, and mcpServers, because nothing it needs sits behind one. A component belongs in an agent only when a question above asks for it. It touches 7 of your 13 components fully (skills, memory, tool use, hooks, evals, guardrails, subagents) and 2 partly (context control through the turn cap and note pruning, and automation, which is prepared but not wired in).

What is checked

Tested, and not tested

  • The scorer passes the good example (10 of 10) and flags the bad one (3 of 10).
  • The hook was run against 14 test calls. It blocked 10 (plain http, file links, localhost, IP addresses, internal names, a username trick, odd ports) and allowed 4.
  • The agent's front matter parses as valid YAML.
  • The agent has not run live yet. Agents load at session start, so it needs a restart first.
  • I have not confirmed that memory: user writes to ~/.claude/agent-memory/ai-news-briefer/, or that skills: loads the full skill text. Check both on the first run.
  • Your scheduled task is unchanged. It runs from the Desktop folder, so the agent has to be copied to ~/.claude/ before the task can use it.

When does adding agents stop paying off?

Three scouts search in parallel and one verifier checks their claims. The same scorer grades both versions, so you get numbers for quality and cost. My pick, because it reuses what exists.
